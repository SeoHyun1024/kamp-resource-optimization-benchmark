# 피크전력 위험 예측 모델

제조 공장의 시간당 최대수요전력을 이용해 **다음 1시간이 피크(≥179)가 될 위험**을 예측합니다. 사용한 모델은 RNN, Random Forest, XGBoost, CatBoost, Isolation Forest, 회귀(XGBoost·LightGBM) 입니다.

## 폴더 구조


## 실행 방법

Python 3.11 기준입니다.

```bash
# 0. 패키지 설치 (처음 한 번)
pip install -r requirements.txt

# 1. 전처리
python preprocessing.py                               # → results/1_preprocessing/

# 2. 모델 학습·평가 (01~06은 서로 독립)
python 01_rnn.py --variant D_multi_gru               # GRU CV + OOF 저장 + 최종 학습, 약 15~25분 (옵션 없이 실행하면 구조 4종 CV 포함 약 1시간)
# python 01_rnn.py --skip-cv --epochs 90              # CV 없이 최종 학습만 (rnn_oof.csv가 안 생겨 09는 실행 불가)
python 02_random_forest.py                            # 약 2분
python 03_xgboost.py                                  # 약 30초
python 04_catboost.py                                 # 약 1분
python 05_isolation_forest.py                         # 약 10초
python 06_regression.py                               # 약 1~2분

# 3. 전체 비교 (반드시 마지막)
python 07_compare.py                                  # → results/3_comparison/final_comparison.csv

# 4. (선택) 보조 실험
python ablation_copied_days.py   # 복제일 처리 비교, 약 1분
python ablation_missing.py       # 결측 처리 비교, 약 4분
python ablation_encoding.py      # 달력 인코딩 비교, 약 1분
python ablation_fp_features.py   # 헛경보 원인 변수 실험, 약 3분

# 5. 에이전트 모듈 (01·02 실행 후)
python 08_operating_calendar.py  # M1 가동 캘린더, 수 초
python 09_peak_alert.py          # M2 피크 경보, 약 10초 (01·02의 OOF·test 예측과 08 결과 사용)
python 10_plan_regression.py     # M3 하루 전 전력 예측, 약 50분 (06·08 결과 사용)
python 11_schedule_adjust.py     # M4 일정 조정, 수 초 (08~10 결과 사용, 표준 라이브러리만 사용)
python 12_build_report.py        # M5 웹 데이터 생성 -> web/data/agent_data.js (11 포함 실행)

# 6. 웹 화면 확인 (서버 불필요: web/index.html 을 바로 열어도 되고, 아래처럼 띄워도 됨)
python -m http.server 8000 --directory web   # http://localhost:8000
```

- `01_rnn.py`를 다시 실행하면 07·09도 함께 다시 실행합니다. 07의 RNN 행과 09의 경보 규칙이 01 결과(cutoff, OOF)를 읽기 때문입니다.
- 다시 실행하면 `results/`의 같은 이름 파일은 덮어써집니다. `07_compare.py`는 02~04의 결과로 앙상블을 만들므로 앞 스크립트를 다시 돌렸다면 함께 다시 실행합니다.

- 모든 스크립트는 `kamp` 폴더에서 실행합니다.
- 시드는 42로 고정했습니다. 다만 CPU나 라이브러리 버전에 따라 소수점 수준의 차이는 날 수 있습니다.

**예측 대상**

- `power` = max(15분, 30분, 45분, 60분): 해당 시간의 최대수요전력입니다.
- 피크 라벨은 `power ≥ 179`입니다. 179는 2021-01-08~07-31 `power`의 90% 분위수예요.

**변환에서 지킨 원칙**

- RNN early stopping은 검증 구간(7·8월)이 아니라 **각 fold 학습 구간의 마지막 원본 14일**(복제일 제외)로 멈출 시점을 정합니다. 검증 구간으로 멈추면 그 구간에 맞춘 셈이 되어 CV 성능이 실제보다 좋게 나오기 때문입니다. 최종 모델은 CV에서 나온 fold별 best epoch의 평균만큼 학습합니다.
- 학습 데이터로 무언가를 맞추는 변환은 **학습 구간으로만** 맞춥니다. MinMax 스케일러, Isolation Forest의 중앙값·판정 경계, 분류 threshold·회귀 cutoff가 여기에 해당하고, CV에서는 fold마다 다시 맞춥니다.
- sin/cos, 범주형 지정, feature 선택처럼 값을 학습하지 않는 변환은 데이터 전체에 같은 규칙으로 적용합니다.
- 모델별 선택의 근거:
  - 달력 인코딩: `ablation_encoding.py`
  - Isolation Forest 입력 구성: `05_isolation_forest.py`의 실험 A~C
  - RNN 입력 구조: `01_rnn.py`의 구조 A~D 비교

## 검증 방식

- **CV**: 확장창 2-fold로 hyperparameter, threshold, 모델 구조를 선택합니다.
  - fold 1: 7/1 이전으로 학습하고 7월로 검증
  - fold 2: 8/1 이전으로 학습하고 8월로 검증
- **최종 학습**: 9/1 이전 전체 데이터로 다시 학습합니다.
- **Test**: 2021-09-01~09-14(336시간, 피크 47건)이며, 선택에는 쓰지 않고 마지막에 1회만 평가합니다.

### M2 피크 경보

RNN(전력 회귀 → cutoff)과 RF(피크 확률 → threshold) 두 모델의 판단을 묶어 **주의 → 확정** 2단계 경보를 냅니다. 각 모델의 기준값(cutoff, threshold)은 01·02가 CV OOF로 고른 값을 `5_models/*_meta.json`에서 읽습니다.

**조합 선택 방법 (test 미사용)**

어떤 조합을 쓸지는 test가 아니라 CV(7·8월, 복제일 제외) OOF 예측으로 정하고, 기준은 결과를 보기 전에 정해 두었습니다.

- **동률 처리**: 1위와 각 후보의 지표 차이를 날짜 단위 부트스트랩(2000회)으로 구해 95% 구간이 0을 포함하면 "차이 없음"으로 보고, 그중 단순한 조합(모델 1개 > 2개)을 고릅니다. 근소한 차이로 복잡한 규칙을 고르지 않기 위해서입니다.
- **fold별 확인**: 7월·8월 각각의 지표를 함께 저장해(`peak_alert_rule_selection.csv`) 한 달에만 좋은 조합인지 확인합니다.
- **test 적용**: 선택된 조합을 9/1~9/14에 한 번만 적용합니다. 다른 후보의 test 성능은 참고로만 출력합니다.
- 확정은 항상 주의에 포함됩니다. 두 단계에 같은 조합이 선택되면 두 번째 확인이 이득이 없다는 뜻이므로 1단계 경보로 운영합니다.

### M3 하루 전 전력 예측

M2는 직전 1시간 전력을 쓰는 1시간 전 예측이라 내일 계획 검토에는 쓸 수 없습니다. M3는 T보다 24시간 이상 앞선 값(22개)과 가동 계획만 쓰는 하루 전 모델입니다(`10_plan_regression.py`).

#### 가동 계획을 무엇으로 만들었나

데이터에는 실제 가동 계획표가 없습니다. 그래서 계획을 두 가지로 만들었습니다.

- **실제 가동**: T 시각 실제 전력 > 41 kW. 예측 대상에서 만든 값이라 하루 전에는 알 수 없습니다.
- **현실 계획**: 요일별 평소 일정 + 미리 공지된 회사 휴무. 하루 전에 알 수 있습니다(구성은 아래).

두 계획을 학습할 때와 예측할 때 어떻게 넣느냐에 따라 실험을 셋으로 나눴습니다.

| 실험              | 학습할 때 | 예측할 때 | 역할                          |
| ----------------- | --------- | --------- | ----------------------------- |
| **B'' 계획 예측** | 실제 가동 | 현실 계획 | **본 모델**                   |
| B' 현실 계획      | 현실 계획 | 현실 계획 | 비교: 학습에도 계획을 쓴 경우 |
| B 실제 가동       | 실제 가동 | 실제 가동 | 계획이 100% 지켜질 때의 상한  |

- B는 예측 시점에 실제 전력에서 만든 값을 쓰므로 하루 전 예측의 용도와 맞지 않고 누수로 읽힐 수 있습니다. 그래서 상한으로만 씁니다.
- **B''가 실제 운영 상황과 같습니다.** 운영에서도 지난 기간은 실제 가동 기록(전력 기록)이 있고, 내일만 계획으로 압니다. 그래서 학습은 실제 가동으로, 예측은 현실 계획으로 합니다. CV에서도 검증 구간에는 그 fold의 현실 계획만 넣습니다.
- 처음에는 B'를 본 모델로 만들었는데 효과가 작았습니다(아래 해석 참고). 학습 기간에 계획과 실제 가동이 자주 어긋나 모델이 계획을 덜 믿도록 배웠기 때문이라고 보고 B''를 추가했고, 실제로 크게 좋아져 본 모델을 B''로 바꿨습니다.
- 본 모델은 예측 시점에 현실 계획만 쓰는 B'·B'' 중 CV MAE가 가장 낮은 모델입니다.

#### 해석

- **현실 계획으로 예측해도 효과가 큽니다(B'').** LightGBM 기준 CV MAE 23.44 → 11.71, test 7.46 → 6.31입니다. test는 하루 전 모델 중 가장 좋고, 1시간 전 모델(6.12)과 0.19 kW 차이입니다.
- **계획이 맞으면 상한에 가깝습니다.** 하계 휴무를 계획으로 알려 준 8월은 B'' 6.81로 상한 B(6.73)와 거의 같습니다. 가동 정보가 없는 A는 8월에 "1주 전 같은 시각"(46.6)처럼 지난 패턴을 따라가다 크게 틀립니다(33.5).
- **계획이 틀리면 그대로 틀립니다.** 7월은 B'' 16.78로 A(13.02)보다 나쁩니다. 7월 무렵 요일 일정이 바뀌어 현실 계획이 7월의 월·목요일마다 어긋났고(일치율 90.1%), B''는 계획을 믿도록 학습했기 때문입니다. **예측 품질이 계획의 질에 달려 있다**는 뜻이며, 실제 운영에서는 공장의 확정 계획표를 넣어야 합니다.
- **학습에도 계획을 쓰면(B') 계획을 덜 믿게 됩니다.** B'는 계획이 99.7% 맞은 8월에도 27.98로 B''(6.81)에 크게 못 미칩니다. 학습 기간(1~7월)에는 계획과 실제 가동이 자주 어긋나서(일정 변경, 일요일 예열 가동 등), 모델이 계획보다 과거 전력에 기대도록 배웠기 때문입니다. 그래서 과거는 실제 가동 기록으로 학습하는 것이 맞습니다.
- 생산량 기록은 CV에서 효과가 없습니다(LightGBM 21.34, XGBoost 23.43). 전력은 생산량의 크기가 아니라 켜짐/꺼짐이 결정합니다.
- **일 최대전력은 여전히 낮게 예측합니다**(본 모델 평균 -7.9 kW, 최대 -24.7 kW). 다만 실제 일 최대가 피크 기준 179를 넘은 10일은 예측 최대도 모두 179를 넘었고, 넘지 않은 날을 넘는다고 한 날은 없습니다. 피크가 "있는 날"은 맞히지만 크기는 작게 봅니다. M4에서 절감량을 계산할 때는 M2 경보와 실제 크기를 함께 봐야 합니다.
- 가동 시작·종료 시각 MAE는 계획을 넣으면 커집니다(A LightGBM 9.99 → B'' 13.66, test 6시간). 켜지는 시각은 알아도 얼마나 빨리 오르는지는 맞히지 못합니다.

### M4 일정 조정

M3의 하루 전 예측과 가동 계획만으로 "내일" 일정을 짜고, 같은 이동량을 **그날의 실제 전력**에 적용해 효과를 확인합니다. 계획은 예측으로, 평가는 실제로 하는 방식입니다(`11_schedule_adjust.py`, 표준 라이브러리만 사용).

**방법** (날짜별, 같은 날 안에서만 이동)

1. **덜어낼 시간**: 계획상 가동 중이고 (예측 + 안전 마진) ≥ 178 kW인 시간. 넘는 만큼만, 최대 '이동 가능 비율'까지 덜어냅니다.
2. **받을 시간**: 가동 중이고 덜어내지 않는 시간 중 예측이 낮은 곳부터. 덜어낼 시간에서 ±6시간 안이고, 받은 뒤에도 (예측 + 마진)이 168 kW 이하가 되게 합니다. 다 옮기지 못한 양은 옮기지 않습니다.
3. **안전 마진**: M3는 일 최대전력을 낮게 예측합니다(편향: 7월 −8.1, 8월 −8.5, test −7.9 kW). 그래서 예측에 마진을 더해서 봅니다. 기본값 8 kW는 **CV 두 달의 편향**에서 정했고 test 결과를 보고 고르지 않았습니다.
4. **이동 가능 비율·기본요금 단가는 데이터에 없는 운영 조건**입니다. 비율은 5~30%, 마진은 0·8·15 kW 격자로 미리 계산해 두고 고르게 했고, 단가는 화면에서 입력합니다(기본 8,000원/kW·월은 **예시값**이며 실제 계약 단가가 아닙니다).

**결과** (test 9/1~9/14, 이동 가능 비율 10%, 실제 전력에 적용)

| 안전 마진 | 피크 시간 (≥179 kW) | 기간 최대수요 | 피크일의 일 최대 평균 감소 |
|---|---|---|---|
| 0 kW | 47 → 39 | 204.0 → 204.0 kW | −1.8 kW |

- 이동 가능 비율은 10%에서 효과가 포화됩니다(15·20·30%도 같은 결과). 덜어낼 양이 기준을 넘는 만큼이라 10%면 충분하기 때문입니다.
- **요금 기준인 기간 최대수요는 1.8 kW만 줄었습니다.** 최대 204 kW는 9/10에 발생했는데 M3는 그날 최대를 179.3 kW로 예측해(25 kW 낮게) 일정 조정 대상에서 사실상 빠졌기 때문입니다. 피크 시간이 크게 줄어도 요금에 쓰이는 값은 이 한 순간으로 정해집니다.
- 마진 15 kW는 최대수요를 195.2 kW까지 낮추지만, 이 값은 민감도 확인용입니다. test를 보고 고르면 안 됩니다.

### 헛경보(FP) 원인 분석 (`ablation_fp_features.py`)

- CV(7·8월)에서 RF 헛경보는 가동 전환 시각(13시 점심 직후, 15~17시 퇴근 전후)에 약 57%가 몰립니다.
  - 15~17시: 직전 시간이 이미 피크여서 모델이 피크가 이어진다고 보지만, 실제로는 내려가며 170~178에 머뭅니다.
  - 13시: 직전 값(점심 시간)이 낮아 정보가 없고 2주 전 같은 시각 최대에 의존합니다.
- 헛경보의 약 64%는 실제 전력 170~178의 경계 사례입니다.
- 시간 내 하락, 피크 지속, 시각별 전환 패턴, 생산 변화 변수(G1~G4)를 추가하면 RF CV 헛경보가 약 14% 줄지만 놓친 피크가 늘고, test에서는 개선이 없었습니다. 교대·점심 시각 같은 작업 스케줄 정보가 데이터에 없어서이며, 향후 과제로 둡니다.

## 저장된 모델 불러오기

```python
import json, joblib
meta = json.load(open("results/5_models/random_forest_meta.json", encoding="utf-8"))
rf = joblib.load("results/5_models/" + meta["model_file"])
proba = rf.predict_proba(X[meta["features"]])[:, 1]          # X = feature 표 (meta["features"] 순서)
peak = proba >= meta["classification_threshold"]              # 피크 위험 판정
```

- XGBoost는 `XGBClassifier().load_model(...)`, CatBoost는 `CatBoostClassifier().load_model(...)`로 불러와요.
- RNN은 `keras.models.load_model("results/5_models/rnn.keras")`로 불러오고, 입력·출력 변환에는 `rnn_scalers.joblib`를 써요.
