# 피크전력 위험 예측 모델

제조 공장의 시간당 최대수요전력을 이용해 **다음 1시간이 피크(≥179)가 될 위험**을 예측합니다. 사용한 모델은 RNN, Random Forest, XGBoost, CatBoost, Isolation Forest, 회귀(XGBoost·LightGBM) 입니다.

## 실행 방법

Python 3.11 기준입니다.

```bash

python 04_catboost.py                                 # 약 1분
```

**예측 대상**

- `power` = max(15분, 30분, 45분, 60분): 해당 시간의 최대수요전력입니다.
- 피크 라벨은 `power ≥ 179`입니다. 179는 2021-01-08~07-31 `power`의 90% 분위수예요.

## Feature (38개, 모두 T−1 시점까지의 정보)

| 그룹                    | Feature                                                                                     |
| ----------------------- | ------------------------------------------------------------------------------------------- |
| 전력 lag                | `lag_1, 2, 3, 6, 12, 24, 48, 167, 168, 169, 336`                                            |
| 직전 1시간 15분 단위 값 | `q15_lag1`, `q30_lag1`, `q45_lag1`, `q60_lag1`, `avg_lag1`, `intra_hour_slope`(60분 − 15분) |
| 추세·통계               | `diff_1`, `roll_mean_3`, `roll_mean_24`, `roll_max_24`, `roll_std_24`, `max_since_midnight` |
| 주간 패턴               | `same_hour_2w_mean`, `same_hour_2w_max`, `last_op_day_same_hour`(직전 가동일 같은 시각)     |
| 전일 상태               | `prev_day_max`, `prev_day_off`                                                              |
| 외생변수(1시간 전)      | 생산량, 기온, 풍속, 습도, 강수량, 전기요금, 공장인원, 인건비                                |
| 달력                    | `hour`, `day_of_week` (RF는 여기에 sin/cos 4개를 더해 42개)                                 |

**누수 점검**: `preprocessing.leakage_checks()`에서 다음을 assert로 확인합니다.

- `lag_1`, `q60_lag1`, `production`이 T−1 값인지
- target과 같거나 상관계수가 0.99 이상인 feature가 없는지

## 모델별 입력 변환 (각 스크립트에서 수행)

모든 모델은 같은 분할·같은 피크 라벨(179)·같은 test(336시간, 피크 47건)를 씁니다. 데이터셋 파일은 공통 1개(`results/1_preprocessing/peak_dataset.csv`)이고, 모델에 맞춘 변환은 각 스크립트가 실행 중에 수행합니다(별도 파일로 저장하지 않음).

| 모델 | 스크립트 | 입력 | 수행하는 변환 |
|---|---|---|---|
| Random Forest | `02_random_forest.py` | 공통 feature 38개 + 4개 = **42개** | `hour`·`day_of_week` 정수에 sin/cos 4개(`hour_sin`, `hour_cos`, `dow_sin`, `dow_cos`)를 추가(`preprocessing.add_cyclic_calendar`). 스케일링 없음 |
| XGBoost | `03_xgboost.py` | 공통 feature **38개** 그대로 | 변환 없음(달력은 정수). `scale_pos_weight`는 학습 구간마다 음성/양성 비율로 다시 계산해 후보로 비교(최종 미사용) |
| CatBoost | `04_catboost.py` | 공통 feature **38개** | `hour`·`day_of_week`를 문자열로 바꿔 `cat_features`(범주형)로 지정. 나머지는 수치 그대로 |
| Isolation Forest | `05_isolation_forest.py` | 전력 관련 feature **21개** | 달력·외생변수를 빼고 전력 lag·15분 값·rolling·주간 패턴만 사용. 학습은 가동 시간대(전일 가동 & 08~18시) 행으로만 함. 점수는 `-decision_function`이며, `lag_1`이 학습 중앙값보다 낮은 시점의 이상은 피크 위험이 아니므로 최저 점수로 보정. 판정 경계는 학습 점수 상위 40% |
| XGBoost·LightGBM 회귀 | `06_regression.py` | 공통 feature **38개** | 라벨 대신 연속값 `target_power`를 예측 대상으로 사용. 예측값 ≥ cutoff(XGB 171, LGBM 173, CV로 선택)이면 피크로 판정 |
| RNN (GRU) | `01_rnn.py` | 시퀀스 **168시간 × 8채널** | `peak_dataset.csv`를 쓰지 않고 같은 정제 과정을 스스로 수행한 뒤, 예측 시점 T마다 T−168~T−1 구간을 잘라 시퀀스를 만듦. 채널은 power, 15분 값, 60분 값, 생산량, 시간 sin/cos, 요일 sin/cos. 입력·target 모두 MinMax 정규화. 예측 시점은 다른 모델과 같은 2021-01-15부터. 예측값 ≥ cutoff면 피크로 판정 (cutoff는 CV OOF F1 최대로 선택: 169) |

**변환에서 지킨 원칙**

- RNN early stopping은 검증 구간(7·8월)이 아니라 **각 fold 학습 구간의 마지막 원본 14일**(복제일 제외)로 멈출 시점을 정합니다. 검증 구간으로 멈추면 그 구간에 맞춘 셈이 되어 CV 성능이 실제보다 좋게 나오기 때문입니다. 최종 모델은 CV에서 나온 fold별 best epoch의 평균만큼 학습합니다.
- 학습 데이터로 무언가를 맞추는 변환은 **학습 구간으로만** 맞춥니다. MinMax 스케일러, Isolation Forest의 중앙값·판정 경계, 분류 threshold·회귀 cutoff가 여기에 해당하고, CV에서는 fold마다 다시 맞춥니다.
- sin/cos, 범주형 지정, feature 선택처럼 값을 학습하지 않는 변환은 데이터 전체에 같은 규칙으로 적용합니다.
- 모델별 선택의 근거:
  - 달력 인코딩: `ablation_encoding.py`
  - Isolation Forest 입력 구성: `05_isolation_forest.py`의 실험 A~C
  - RNN 입력 구조: `01_rnn.py`의 구조 A~D 비교

## 검증 방식

- **CV**: 확장창 2-fold로 hyperparameter, threshold, 모델 구조를 선택합니다.
  - fold 1: 7/1 이전으로 학습하고 7월로 검증
  - fold 2: 8/1 이전으로 학습하고 8월로 검증
- **최종 학습**: 9/1 이전 전체 데이터로 다시 학습합니다.
- **Test**: 2021-09-01~09-14(336시간, 피크 47건)이며, 선택에는 쓰지 않고 마지막에 1회만 평가합니다.

- CV MAE는 early stopping을 학습 구간 마지막 원본 14일로 판단하도록 바꾼 뒤의 값입니다. 이전(검증 구간으로 판단)보다 모두 커졌는데, 이전 값이 검증 구간에 맞춰 낙관적이었기 때문입니다. 구조 순위는 같습니다.
- GRU의 fold별 best epoch는 148, 149로 최대 epoch(150)에 가깝습니다. `--max-epochs`를 늘리면 성능이 더 오를 여지가 있습니다.

### 해석

1. **지도학습 모델은 모두 규칙 기반 기준선보다 좋습니다.** RF, XGBoost, CatBoost, RNN, 회귀 모델의 F1은 0.68~0.73입니다.
   - 규칙 기반 기준선은 직전 값 0.447, 1주 전 같은 시각 0.653입니다.
2. **모델 간 차이는 통계적으로 확정할 수 없습니다.**
   - test가 14일(피크 47건)뿐이라 F1 95% 신뢰구간 폭이 약 ±0.15입니다.
   - 신뢰구간은 일 단위 블록 부트스트랩(2000회)으로 구했습니다.
   - 그래서 모델을 고를 때는 CV 지표와 함께 판단합니다.
3. **test F1은 Random Forest(0.729)가 가장 높습니다.**
   - RF는 Recall 0.915(놓친 피크 4건), Precision 0.606이며, 학습 시간이 짧고 변수 중요도를 바로 볼 수 있습니다.
   - RNN은 전력값 자체를 가장 정확히 맞히지만(test MAE 6.44), 피크 판정 F1은 0.689(Recall 0.894, Precision 0.560)입니다. CV F1은 0.826으로 RF(0.821)와 비슷합니다.
4. **Isolation Forest는 라벨 없이 동작하지만 성능이 낮습니다.**
   - F1 0.485로, 1주 전 같은 시각 규칙보다도 낮습니다.
   - 라벨이 없는 신규 설비용 참고 모델로만 둡니다.
5. **중요 변수**: 1·2주 전 같은 시각 전력(`same_hour_2w_max`), 직전 시간 마지막 15분 값(`q60_lag1`), 시간대(`hour`)가 모든 모델에서 상위권입니다.
   - 즉 공장의 **주간 가동 패턴**과 **직전 추세**가 피크를 가장 잘 설명합니다.

### M2 피크 경보

RNN(전력 회귀 → cutoff)과 RF(피크 확률 → threshold) 두 모델의 판단을 묶어 **주의 → 확정** 2단계 경보를 냅니다. 각 모델의 기준값(cutoff, threshold)은 01·02가 CV OOF로 고른 값을 `5_models/*_meta.json`에서 읽습니다.

**조합 선택 방법 (test 미사용)**

어떤 조합을 쓸지는 test가 아니라 CV(7·8월, 복제일 제외) OOF 예측으로 정하고, 기준은 결과를 보기 전에 정해 두었습니다.

| 단계 | 후보                          | 선택 기준 | 이유                                                              |
| ---- | ----------------------------- | --------- | ----------------------------------------------------------------- |
| 주의 | RNN 단독 / RF 단독 / AND / OR | F2 최대   | 놓친 피크를 줄이는 것이 우선 (Recall에 가중)                      |
| 확정 | 주의에 포함되는 조합          | F0.5 최대 | 실제 조치 대상이므로 헛경보를 줄이는 것이 우선 (Precision에 가중) |

- **동률 처리**: 1위와 각 후보의 지표 차이를 날짜 단위 부트스트랩(2000회)으로 구해 95% 구간이 0을 포함하면 "차이 없음"으로 보고, 그중 단순한 조합(모델 1개 > 2개)을 고릅니다. 근소한 차이로 복잡한 규칙을 고르지 않기 위해서입니다.
- **fold별 확인**: 7월·8월 각각의 지표를 함께 저장해(`peak_alert_rule_selection.csv`) 한 달에만 좋은 조합인지 확인합니다.
- **test 적용**: 선택된 조합을 9/1~9/14에 한 번만 적용합니다. 다른 후보의 test 성능은 참고로만 출력합니다.
- 확정은 항상 주의에 포함됩니다. 두 단계에 같은 조합이 선택되면 두 번째 확인이 이득이 없다는 뜻이므로 1단계 경보로 운영합니다.
- 전환 시각(13·15·16·17시) 경보에는 헛경보 확인 안내가 붙고, 두 모델 판단이 갈린 시간은 `model_disagree`로 표시합니다.
- `rnn_oof.csv`와 `rnn_meta.json`이 다른 실행에서 나온 경우(예: 01을 중간에 멈춘 경우) 경고를 출력합니다.

**선택 결과 (CV OOF 61일, 피크 252건)**: 기준값 RNN ≥ 169, RF ≥ 0.55

| 단계 | 후보 | CV 지표 | 1위와 차이 95% 구간 | 7월 / 8월 | 결과 |
|---|---|---|---|---|---|
| 주의 (F2) | OR | **0.871** | 1위 | 0.842 / 0.912 | 1위지만 모델 2개 |
| | RF 단독 | 0.863 | [−0.004, 0.023] | 0.843 / 0.892 | **선택** (차이 없음 + 모델 1개) |
| | RNN 단독 | 0.853 | [−0.006, 0.048] | 0.806 / 0.921 | 차이 없음 |
| | AND | 0.845 | [0.000, 0.058] | 0.807 / 0.900 | 차이 없음 |
| 확정 (F0.5) | AND (RF + RNN) | **0.822** | 1위 | 0.823 / 0.820 | **선택** |
| | RF 단독 | 0.783 | [0.009, 0.069] | 0.777 / 0.793 | 유의하게 낮음 |

- 주의는 네 조합 모두 1위(OR)와 차이를 확정할 수 없어 가장 단순한 RF 단독을 골랐습니다. 두 달 모두에서 순위가 비슷해 한 달에만 좋은 조합은 아닙니다.
- 확정은 RF에 RNN 확인을 더한 AND가 CV에서 헛경보를 71건 → 49건으로 줄여 F0.5가 유의하게 높았습니다.

**test 적용 결과 (14일, 피크 47건)**

| 단계 | 선택된 조합 | 경보 | 맞힌 피크 | 헛경보 | 놓친 피크 | Precision | Recall | F1 | 하루당 헛경보 |
|---|---|---|---|---|---|---|---|---|---|
| 주의 이상 | RF 단독 | 71 | 43 | 28 | 4 | 0.606 | 0.915 | 0.729 | 2.0 |
| 확정 | AND (RF + RNN) | 68 | 40 | 28 | 7 | 0.588 | 0.851 | 0.696 | 2.0 |

- **test에서는 확정 단계의 이득이 재현되지 않았습니다.** RNN 확인이 헛경보를 하나도 줄이지 못하고 맞힌 피크 3건만 걸러냈습니다. CV에서는 효과가 있었지만 test 14일에서는 반대였으므로, 확정 단계는 운영 데이터로 재검증이 필요합니다.
- 참고로 test에서 OR는 F1 0.720(놓친 피크 2건), RNN 단독은 0.689였습니다. 선택에는 쓰지 않았습니다.
- 이전 버전("주의 = RNN ≥ 167, 확정 = + RF ≥ 0.55", test F1 0.732 / 0.741)은 test 결과를 보고 정한 규칙이라 지금 결과와 직접 비교하지 않습니다.

### M3 하루 전 전력 예측

M2는 직전 1시간 전력을 쓰는 1시간 전 예측이라 내일 계획 검토에는 쓸 수 없습니다. M3는 T보다 24시간 이상 앞선 값(22개)과 가동 계획만 쓰는 하루 전 모델입니다(`10_plan_regression.py`).

#### 가동 계획을 무엇으로 만들었나

데이터에는 실제 가동 계획표가 없습니다. 그래서 계획을 두 가지로 만들었습니다.

- **실제 가동**: T 시각 실제 전력 > 41 kW. 예측 대상에서 만든 값이라 하루 전에는 알 수 없습니다.
- **현실 계획**: 요일별 평소 일정 + 미리 공지된 회사 휴무. 하루 전에 알 수 있습니다(구성은 아래).

두 계획을 학습할 때와 예측할 때 어떻게 넣느냐에 따라 실험을 셋으로 나눴습니다.

| 실험              | 학습할 때 | 예측할 때 | 역할                          |
| ----------------- | --------- | --------- | ----------------------------- |
| **B'' 계획 예측** | 실제 가동 | 현실 계획 | **본 모델**                   |
| B' 현실 계획      | 현실 계획 | 현실 계획 | 비교: 학습에도 계획을 쓴 경우 |
| B 실제 가동       | 실제 가동 | 실제 가동 | 계획이 100% 지켜질 때의 상한  |

- B는 예측 시점에 실제 전력에서 만든 값을 쓰므로 하루 전 예측의 용도와 맞지 않고 누수로 읽힐 수 있습니다. 그래서 상한으로만 씁니다.
- **B''가 실제 운영 상황과 같습니다.** 운영에서도 지난 기간은 실제 가동 기록(전력 기록)이 있고, 내일만 계획으로 압니다. 그래서 학습은 실제 가동으로, 예측은 현실 계획으로 합니다. CV에서도 검증 구간에는 그 fold의 현실 계획만 넣습니다.
- 처음에는 B'를 본 모델로 만들었는데 효과가 작았습니다(아래 해석 참고). 학습 기간에 계획과 실제 가동이 자주 어긋나 모델이 계획을 덜 믿도록 배웠기 때문이라고 보고 B''를 추가했고, 실제로 크게 좋아져 본 모델을 B''로 바꿨습니다.
- 본 모델은 예측 시점에 현실 계획만 쓰는 B'·B'' 중 CV MAE가 가장 낮은 모델입니다.

**현실 계획의 구성과 근거** (근거 수치는 M1 원본 일자 결과)

1. **요일별 평소 일정**: 학습 기간 원본 일자에서 요일·시각별 가동 비율이 0.5를 넘으면 그 시각을 가동으로 봅니다.
   - 근거: 원본 일자의 날 유형이 요일에 따라 뚜렷하게 갈립니다.

     | 날 유형 (원본 142일) | 월  | 화  | 수  | 목  | 금  | 토  | 일  |
     | -------------------- | --- | --- | --- | --- | --- | --- | --- |
     | 종일 가동            | 7   | 14  | 15  | 12  | 16  | 2   | 2   |
     | 가동 시작일          | 13  | 0   | 1   | 6   | 1   | 0   | 3   |
     | 가동 종료일          | 0   | 0   | 2   | 0   | 3   | 16  | 0   |
     | 중간 정지            | 0   | 0   | 0   | 0   | 0   | 2   | 1   |
     | 비가동               | 1   | 2   | 1   | 1   | 1   | 2   | 18  |

   - 9/1 이전 데이터로 뽑은 계획: 월 7~23시, 화~금 종일, 토 0~7시, 일 비가동. 요일·시각별 가동 비율은 `4_model_details/plan_regression_weekday_pattern.csv`에 있습니다.
   - 공휴일 달력이 아니라 **실제로 돈 요일별 패턴**을 씁니다. 원본 공휴일 4일(1/1, 5/5, 5/19, 8/16)이 모두 가동했고 달력과 실제 가동이 다른 날이 25.4%라, 달력으로는 가동 여부를 4일 중 1일꼴로 틀립니다(3.5절에서 달력 변수를 제거한 근거와 같음).
   - **CV fold마다 그 fold의 검증 시작 전 데이터로만** 패턴을 뽑습니다(7월 fold는 7/1 이전, 8월 fold는 8/1 이전, 최종 모델은 9/1 이전). 검증 구간의 가동 정보가 계획에 섞이지 않게 하기 위해서입니다.
   - 복제일과 회사 휴무일은 패턴을 뽑을 때 뺍니다.

2. **회사 휴무 계획**: 미리 공지되는 휴무일은 종일 비가동으로 둡니다. 1/5와 8/2~8/8, 총 8일입니다.
   - 근거: 원본 평일 중 쉰 날은 1/5와 하계 휴무(8/2~8/6) 6일뿐입니다. 공휴일은 모두 가동했으므로 휴무로 넣지 않습니다.
   - 1/5는 신정 연휴 다음 날 화요일입니다. 연초 휴무는 보통 미리 공지되므로 계획된 휴무로 봅니다. 빼면 1/5와 그 복사본인 증강일 12일이 "계획은 가동인데 실제는 비가동"인 날이 되어, 학습에 계획을 쓰는 B'에서는 모델이 계획을 덜 믿도록 배웁니다.
   - 하계 휴무는 주말까지 한 주(8/2~8/8)로 둡니다. 실제로 8/7(토)도 쉬었고(평소 토요일은 오전 가동), 하계 휴무는 보통 한 주 단위로 공지됩니다.
3. **복제일은 원본 날짜의 계획을 물려받습니다.**
   - 근거: 복제일 115일은 다른 날짜의 전력을 그대로 복사한 날이라 전력 패턴이 그날 요일이 아니라 원본 날짜를 따릅니다(예: 화요일에 일요일 패턴). 그날 요일의 계획을 붙이면 학습 데이터에 계획과 전력이 어긋난 날이 대량으로 생깁니다.
   - CV 검증 구간과 test에는 복제일이 없어 평가 수치에는 영향이 없습니다. 학습에 계획을 쓰는 B'의 학습 데이터만 정상이 됩니다(B''는 학습에 실제 가동을 씀).

#### 해석

- **현실 계획으로 예측해도 효과가 큽니다(B'').** LightGBM 기준 CV MAE 23.44 → 11.71, test 7.46 → 6.31입니다. test는 하루 전 모델 중 가장 좋고, 1시간 전 모델(6.12)과 0.19 kW 차이입니다.
- **계획이 맞으면 상한에 가깝습니다.** 하계 휴무를 계획으로 알려 준 8월은 B'' 6.81로 상한 B(6.73)와 거의 같습니다. 가동 정보가 없는 A는 8월에 "1주 전 같은 시각"(46.6)처럼 지난 패턴을 따라가다 크게 틀립니다(33.5).
- **계획이 틀리면 그대로 틀립니다.** 7월은 B'' 16.78로 A(13.02)보다 나쁩니다. 7월 무렵 요일 일정이 바뀌어 현실 계획이 7월의 월·목요일마다 어긋났고(일치율 90.1%), B''는 계획을 믿도록 학습했기 때문입니다. **예측 품질이 계획의 질에 달려 있다**는 뜻이며, 실제 운영에서는 공장의 확정 계획표를 넣어야 합니다.
- **학습에도 계획을 쓰면(B') 계획을 덜 믿게 됩니다.** B'는 계획이 99.7% 맞은 8월에도 27.98로 B''(6.81)에 크게 못 미칩니다. 학습 기간(1~7월)에는 계획과 실제 가동이 자주 어긋나서(일정 변경, 일요일 예열 가동 등), 모델이 계획보다 과거 전력에 기대도록 배웠기 때문입니다. 그래서 과거는 실제 가동 기록으로 학습하는 것이 맞습니다.
- 생산량 기록은 CV에서 효과가 없습니다(LightGBM 21.34, XGBoost 23.43). 전력은 생산량의 크기가 아니라 켜짐/꺼짐이 결정합니다.
- **일 최대전력은 여전히 낮게 예측합니다**(본 모델 평균 -7.9 kW, 최대 -24.7 kW). 다만 실제 일 최대가 피크 기준 179를 넘은 10일은 예측 최대도 모두 179를 넘었고, 넘지 않은 날을 넘는다고 한 날은 없습니다. 피크가 "있는 날"은 맞히지만 크기는 작게 봅니다. M4에서 절감량을 계산할 때는 M2 경보와 실제 크기를 함께 봐야 합니다.
- 가동 시작·종료 시각 MAE는 계획을 넣으면 커집니다(A LightGBM 9.99 → B'' 13.66, test 6시간). 켜지는 시각은 알아도 얼마나 빨리 오르는지는 맞히지 못합니다.
- 가이드북 비교용 MSE는 83.74입니다(= RMSE²). 예측 대상 정의가 같은지 확인한 뒤 써야 합니다.

### M4 일정 조정

M3의 하루 전 예측과 가동 계획만으로 "내일" 일정을 짜고, 같은 이동량을 **그날의 실제 전력**에 적용해 효과를 확인합니다. 계획은 예측으로, 평가는 실제로 하는 방식입니다(`11_schedule_adjust.py`, 표준 라이브러리만 사용).

**방법** (날짜별, 같은 날 안에서만 이동)

1. **덜어낼 시간**: 계획상 가동 중이고 (예측 + 안전 마진) ≥ 178 kW인 시간. 넘는 만큼만, 최대 '이동 가능 비율'까지 덜어냅니다.
2. **받을 시간**: 가동 중이고 덜어내지 않는 시간 중 예측이 낮은 곳부터. 덜어낼 시간에서 ±6시간 안이고, 받은 뒤에도 (예측 + 마진)이 168 kW 이하가 되게 합니다. 다 옮기지 못한 양은 옮기지 않습니다.
3. **안전 마진**: M3는 일 최대전력을 낮게 예측합니다(편향: 7월 −8.1, 8월 −8.5, test −7.9 kW). 그래서 예측에 마진을 더해서 봅니다. 기본값 8 kW는 **CV 두 달의 편향**에서 정했고 test 결과를 보고 고르지 않았습니다.
4. **이동 가능 비율·기본요금 단가는 데이터에 없는 운영 조건**입니다. 비율은 5~30%, 마진은 0·8·15 kW 격자로 미리 계산해 두고 고르게 했고, 단가는 화면에서 입력합니다(기본 8,000원/kW·월은 **예시값**이며 실제 계약 단가가 아닙니다).

**결과** (test 9/1~9/14, 이동 가능 비율 10%, 실제 전력에 적용)

| 안전 마진 | 피크 시간 (≥179 kW) | 기간 최대수요 | 피크일의 일 최대 평균 감소 |
|---|---|---|---|
| 0 kW | 47 → 39 | 204.0 → 204.0 kW | −1.8 kW |
| **8 kW (기본)** | **47 → 26** | **204.0 → 202.2 kW** | **−7.8 kW** |
| 15 kW (민감도) | 47 → 8 | 204.0 → 195.2 kW | −12.8 kW |

- 이동 가능 비율은 10%에서 효과가 포화됩니다(15·20·30%도 같은 결과). 덜어낼 양이 기준을 넘는 만큼이라 10%면 충분하기 때문입니다.
- **요금 기준인 기간 최대수요는 1.8 kW만 줄었습니다.** 최대 204 kW는 9/10에 발생했는데 M3는 그날 최대를 179.3 kW로 예측해(25 kW 낮게) 일정 조정 대상에서 사실상 빠졌기 때문입니다. 피크 시간이 크게 줄어도 요금에 쓰이는 값은 이 한 순간으로 정해집니다.
- 마진 15 kW는 최대수요를 195.2 kW까지 낮추지만, 이 값은 민감도 확인용입니다. test를 보고 고르면 안 됩니다.
- 조정 후에도 남은 피크 26시간 중 23시간은 당일 M2가 이미 '주의' 이상으로 경보했습니다. 하루 전 계획(M3·M4)이 놓친 것을 당일 경보(M2)가 이어받는 구조입니다.
- 한계: 작업별 이동 가능 여부, 점심·교대 시간, 인원은 데이터에 없어 반영하지 못했습니다. 낮 부하를 새벽·야간으로 옮기면 야간 인건비(인건비 비율 1.5)가 늘 수 있는데 이 비용도 계산에 없습니다.

### M4 일정 조정 시뮬레이션

피크 경보가 난 시간의 부하 일부를 같은 날 다른 시간으로 옮기면 최대수요가 얼마나 줄어드는지 계산합니다(`11_schedule_simulation.py`). 모델을 F1이 아니라 절감 효과로 비교하기 위한 단계입니다.

#### 무엇을 계산하나

- 전기요금 열에는 계절 단가 3개(109.8 / 167.2 / 191.6)만 있어, 부하를 다른 시간으로 옮겨도 전력량요금은 변하지 않습니다.
- 절감은 최대수요로 정해지는 **기본요금**에서만 나옵니다. 그래서 주 지표는 기간 최대수요 감소량(kW)입니다.
- 실제 모델 예측을 그대로 씁니다. 놓친 피크는 깎지 못하고, 헛경보는 불필요한 조정이 됩니다.

#### 가정과 근거

| 규칙 | 근거 | 검토한 대안과 버린 이유 |
| --- | --- | --- |

#### 해석

- **깎을 수 있는 최대수요에는 한계가 있습니다.** test는 피크가 아닌 시간의 최대가 178 kW라 26 kW(204 → 178)가 이론상 한계입니다. 완벽 예측으로도 1시간 전에는 12.0 kW, 하루 전에는 22.0 kW까지만 줄었습니다. 1시간 전 경보는 x를 10%에서 20%로 올려도 12.0 kW 그대로인데, 받을 곳이 이후 시간뿐이라 못 옮긴 양만 134 → 394 kW로 늘기 때문입니다.
- **언제 아느냐가 얼마나 정확하냐보다 중요합니다.** test x = 10%에서 M2 주의·확정·RNN 단독은 모두 12.0 kW로 1시간 전 상한과 같고, M3 하루 전은 18.0 kW(하루 전 상한의 88%)입니다. M3는 피크 시간 오차가 더 크지만 전날에 알기 때문에 앞 시간으로도 옮길 수 있습니다. 8월은 반대로 M3가 3.0 kW(14%)에 그쳤는데, 최대 시간(8/11 8시, 218 kW)은 깎았지만 그다음으로 높은 8/9 8시(215 kW)에 경보를 내지 못했기 때문입니다. 하루 전 예측은 효과가 크지만 기간에 따라 편차가 큽니다.
- **F1 순위와 절감 순위는 다릅니다.** test F1은 M2 주의(RF) 0.729, 확정(AND) 0.696, RNN 0.689로 다르지만 최대수요 감소량은 같습니다. 최대수요를 정하는 상위 시간은 세 대상 모두 경보를 냈기 때문입니다. 차이는 불필요한 조정 수(28 / 28 / 33건)와 못 깎은 피크 수(4 / 7 / 5건)에서만 납니다. 1주 전 같은 시각 규칙은 최대 시간(9/10 9시)을 놓쳐 감소량이 0입니다.
- **예측으로 받는 시간을 고르면 새 피크가 생깁니다.** test x = 10%에서 M2 주의는 받는 시간 7곳이 새로 피크가 됐고, 옮기려던 양의 26%(335 kW)는 받을 곳이 없어 못 옮겼습니다. 7월 x = 20%에서는 M2 주의, M3 하루 전, 1주 전 규칙 모두 최대수요가 9.2 kW 늘었습니다. 7/15 22시가 실제 202 kW인데 예상 부하가 146 kW라 29 kW를 받아 231 kW가 됐습니다. 7/15는 원자료의 시간 값이 깨져 있던 날입니다.
- **x를 키운다고 더 줄지 않습니다.** test의 M2 주의는 5% 10.2, 10% 12.0, 20% 9.0 kW입니다. 많이 옮길수록 받는 쪽 위험이 커지므로, 이 데이터에서는 10% 안팎이 가장 안전합니다.
- **첫 해에는 요금이 줄지 않습니다.** 12개월 기준으로는 절감액이 0원입니다. 일정 조정은 한 달만 해서는 효과가 없고, 겨울·여름 피크를 포함해 1년 내내 최대수요를 낮춰야 다음 해 요금적용전력이 내려갑니다. 당월 기준으로 보면 test x = 10%의 M2 주의는 99,840원(기본요금의 5.9%), M3 하루 전은 149,760원(8.8%)입니다.
- **7·8월과 test의 결론은 대체로 같습니다.** M2 계열은 8월과 test에서 약 11 ~ 12 kW로 1시간 전 상한에 닿습니다. 7월만 x가 커질수록 나빠지는데, 요일 일정이 바뀌어 M3 예측과 현실 계획이 어긋난 달입니다(M3 절 참고).

#### 한계

- 이동 가능 비율 x는 가정입니다. 설비별 데이터가 없어 어느 부하를 얼마나 옮길 수 있는지는 확인하지 못했습니다.
- 받는 시간이 예상 부하의 x%까지 더 받을 수 있다는 것도 가정입니다. 이 한도가 없으면 최대수요가 커지는 것을 7·8월에서 확인하고 넣었습니다.
- 설비 위치·작업자 이동 데이터가 없어 물리적 동선은 분석하지 않았습니다. 결과는 가동 일정 조정의 효과입니다.
- 시간 단위 최대수요로 계산했습니다. 실제 요금은 15분 단위 최대수요로 정해집니다.
- 이 공장의 요금제와 계약전력은 확인하지 못했습니다. 절감액은 참고 값입니다.
- test는 14일이라 월 요금으로 볼 수 없습니다.

- 계획 CSV는 1주 전 예측이라 **데이터 마지막 날(9/14) 다음 날부터 7일(9/15~9/21)**까지 넣을 수 있다. 데이터 안의 날짜로 시작하면 백테스트.
- 13 (1주 전 예측): 전력·기온은 T-168시간 이전 값만 쓰고, 가동 여부·생산량 계획을 넣는다. 생산량·가동에는 단조 제약(+).
  test MAE 6.44 kW (하루 전 M3 6.31), 7·8월 CV MAE 8.34 (계획 없이 23.4).
- 14 (계획 수정 제안): 목표는 **일 최대전력 낮추기** (점수 = 날마다 최대의 합 + 2 × 주간 최대 + 0.2 × 위험 초과량).
  주간 총 생산량은 그대로 두고 1) 같은 날 시간 이동, 2) 최대가 높은 날의 하루 생산량 10·20·30%를 여유 있는 날로 이동한다.
  `--allow-new-hours`는 과거에 선례(같은 요일·시각 가동 5% 이상)가 있는 비가동 시간만 켜서 가동 구간을 늘린다(실험적).
  하루 계획 생산량이 과거 99% 분위수보다 많은 날은 '범위 밖'으로 표시한다(모델이 물량 변화에 둔감해 결과를 믿기 어려움).
- 결과 (웹 예시):

  | 주 | 수정 범위 | 주간 예측 최대 | 일 최대가 내려간 날 | 받는 날 최대 상승 | 옮긴 물량 | 실제 피크 시간(추정) |
  |---|---|---|---|---|---|---|
  | 9/8~14 백테스트 | 기본안 | 194.9 → 186.0 | 4일, 평균 −6.5 | +6.8 | 27.7% | 22 → 14 |
  | 9/8~14 백테스트 | 적극안 | 194.9 → 183.7 | 5일, 평균 −8.6 | +12.9 | 40.4% | 22 → 14 |
  | 9/15~21 평소 일정 | 기본안 | 191.4 → 188.1 | 3일, 평균 −5.0 | +7.4 | 19.2% | - |
  | 9/15~21 평소 일정 | 적극안 | 191.4 → 180.1 | 5일, 평균 −11.6 | +27.1 (토요일 11시간 새로 가동) | 51.3% | - |

- 한계: 평일 낮 전력은 생산량보다 가동 자체에 좌우되어 줄이는 폭이 날마다 몇~10 kW 수준. 남는 피크는 M2 경보로 대응.
  물량을 받는 날(주로 토요일)의 야간 인건비·인력은 반영하지 않음. 실제 피크 추정은 실제 전력 + 모델이 본 변화량.
- 웹: '주간 계획' 탭에서 주·수정 범위를 고르고, 챗봇은 9/15 이후 날짜나 "주간 계획/수정안/다음 주"를 물으면 이 결과로 답한다.
